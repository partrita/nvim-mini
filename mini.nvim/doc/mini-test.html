mini.test 문서

_ ’mini.nvim’의 main 브랜치에서 생성됨 _

mini.test Neovim 플러그인 테스트

MIT 라이선스 Copyright (c) 2022 Evgeni Chasnovski

모듈

기능:

  • 테스트 동작은 테이블의 이름이 있는 호출 가능한 엔트리로 정의됩니다.

  • 테스트에서 사용하도록 설계된 자식 Neovim 프로세스를 생성하기 위한 헬퍼입니다 (스크린샷 촬영 및 검증 포함). MiniTest.new_child_neovim() 및 MiniTest.expect.reference_screenshot()를 참조하세요.

  • 커스텀 훅, 매개변수화 및 사용자 데이터를 사용한 테스트의 계층적 구조화. MiniTest.new_set()을 참조하세요.

  • lunarmodules/busted 인터페이스 (describe, it 등) 에뮬레이션.

  • 미리 정의된 작지만 유용한 기대치 (assert와 유사한 함수) 세트. MiniTest.expect를 참조하세요.

  • 어떤 파일을 테스트해야 하는지에 대한 커스터마이징 가능한 정의.

  • 테스트 케이스 필터링. 파일 테스트를 위한 미리 정의된 래퍼(MiniTest.run_file())와 현재 커서 위치와 같은 위치에서의 케이스 테스트(MiniTest.run_at_location())가 있습니다.

  • 커스터마이징 가능한 출력 결과 리포터. 두 가지 미리 정의된 리포터가 있습니다:

    • 대화형 사용을 위한 MiniTest.gen_reporter.buffer().

    • 헤드리스 Neovim을 위한 MiniTest.gen_reporter.stdout().

  • 커스터마이징 가능한 프로젝트별 테스트 스크립트.

  • Unix (Linux, MacOS 등) 및 Windows에서 작동합니다.

지원하지 않는 기능:

  • 병렬 실행. 구현 복잡성을 제한하기 위함입니다.

  • Mock, stub 등. 자식 Neovim 프로세스를 사용하고 필요한 것을 수동으로 재정의하세요. 그 후 자식 프로세스를 재설정하세요.

  • “지나치게 구체적인” 기대치. (비)동등성 및 에러 (부재)에 대한 테스트는 대개 대부분의 요구 사항을 충족합니다. 새로운 기대치를 추가하는 것은 추가적인 구현 복잡성에 비해 유용성이 얼마나 큰지 따져봐야 합니다. 커스텀 기대치를 만들려면 MiniTest.new_expectation()을 사용하세요.

자세한 내용은 다음을 참조하세요:

  • 예제 기반의 실무 소개는 ‘TESTING.md’ 파일을 참조하세요.

  • 이 플러그인의 테스트 코드를 참조하세요. ’mini.test’를 사용하여 테스트를 조직하고 생성하는 의도된 방식의 예제로 간주하세요.

워크플로우

  • 테스트를 별도의 파일로 조직합니다. 각 테스트 파일은 (명시적으로 또는 “busted” 스타일 함수를 사용하여 암시적으로) 테스트 세트를 반환해야 합니다.

  • 테스트 동작을 테스트 세트의 호출 가능한 엔트리로 작성합니다. 테스트 동작 내부에서 자식 프로세스(MiniTest.new_child_neovim() 참조)와 내장 기대치(MiniTest.expect 참조)를 사용합니다.

  • 테스트를 실행합니다. 이는 두 단계로 이루어집니다:

    • 수집(Collect). 이는 단일 계층적 테스트 세트를 생성하고, 매개변수화로 확장하면서 테스트 케이스 배열(MiniTest-test-case 참조)로 평탄화하고, 필터링할 수도 있습니다.

    • 실행(Execute). 이는 비동기 방식으로 진행 상황을 보고할 수 있도록 허용하면서 지정된 순서대로 훅과 메인 테스트 동작을 안전하게 호출합니다. 에러가 감지되면 테스트 케이스 실패를 의미하며, 그렇지 않으면 성공입니다.

설정

이 모듈은 require('mini.test').setup({}) 호출을 통한 설정이 필요합니다 ({}를 config 테이블로 교체하세요). 이는 스크립팅이나 수동으로 (:lua MiniTest.*를 사용하여) 사용할 수 있는 전역 Lua 테이블 MiniTest를 생성합니다.

사용 가능한 설정 옵션은 MiniTest.config를 참조하세요.

MiniTest.config와 동일한 구조를 가져야 하는 vim.b.minitest_config를 사용하여 버퍼별로 런타임 설정을 로컬에서 재정의할 수 있습니다. 자세한 내용은 mini.nvim-buffer-local-config를 참조하세요.

모듈이 에러가 아닌 피드백을 표시하지 않게 하려면 config.silent = true로 설정하세요.

비교

  • nvim-lua/plenary.nvim의 테스트 인프라:

    • 커스터마이징 가능한 ‘init.vim’ 파일을 사용하여 각 파일을 별도의 헤드리스 Neovim 프로세스에서 실행합니다. 반면 ’mini.test’는 현재 Neovim 프로세스에서 모든 것을 실행하며, 수동으로 관리되는 자식 Neovim 프로세스(MiniTest.new_child_neovim() 참조)를 사용하여 테스트를 작성하도록 권장합니다.

    • 테스트는 ‘lunarmodules/busted’ 및 ’lunarmodules/luassert’의 간소화된 내장 버전을 사용하여 작성될 것으로 예상됩니다. 반면 ’mini.test’는 테스트 세트(MiniTest.new_set() 참조)와 테스트 케이스(MiniTest-test-case 참조)의 개념을 사용합니다. 또한 “busted” 프레임워크의 더 큰 부분을 에뮬레이션할 수 있습니다.

    • 진행 상황을 보고하는 단일 방식(요약 없이 매 케이스 후 결과 표시)만 있습니다. 반면 ’mini.test’는 대화형 및 헤드리스 사용을 위한 기본값이 있는 커스터마이징된 리포터를 가질 수 있습니다 (더 작고 사용자 친화적인 요약을 제공합니다).

    • 병렬 실행을 허용하지만, ’mini.test’는 허용하지 않습니다.

    • Mock, stub, spy 생성을 허용하지만, ’mini.test’는 자식 Neovim 프로세스에서 기능을 수동으로 재정의하는 방식을 선호하여 허용하지 않습니다.

’mini.test’는 “busted 스타일” 테스트 에뮬레이션을 지원하지만, 설계된 테스트 정의 방식(MiniTest.new_set() 및 명시적 테이블 필드 사용)을 사용하는 것이 더 안정적입니다. 몇 가지 이유:

  • “Busted” 구문은 ’mini.test’가 제공하는 모든 기능을 지원하지 않습니다. 주로 매개변수화 및 테스트 세트에 사용자 데이터 제공에 관한 것입니다.

  • 이는 에뮬레이션이지 완전한 지원이 아닙니다. 따라서 일부 미묘한 부분이 예상대로 작동하지 않을 수 있습니다.

‘plenary.nvim’ 테스트를 ’mini.test’로 변환하기 위한 몇 가지 힌트:

  • 파일 이름을 “spec.lua”에서 ”test.lua”로 변경하고 “tests” 디렉토리에 넣습니다.

  • assert 호출을 ‘mini.test’ 기대치로 교체합니다. MiniTest.expect를 참조하세요.

  • 메인 테스트 세트 T = MiniTest.new_set()을 생성하고 최종적으로 반환합니다.

  • describe 블록에서 새로운 세트(MiniTest.new_set())를 만듭니다. before_each() 및 after_each를 pre_case 및 post_case 훅으로 변환합니다.

  • it 블록에서 테스트 케이스를 만듭니다.

하이라이트 그룹

  • MiniTestEmphasis - 강조 하이라이팅. 기본적으로 굵은 텍스트입니다.

  • MiniTestFail - 실패한 케이스의 하이라이팅. 기본적으로 vim.g.terminal_color_1 색상(빨간색)의 굵은 텍스트입니다.

  • MiniTestPass - 통과한 케이스의 하이라이팅. 기본적으로 vim.g.terminal_color_2 색상(초록색)의 굵은 텍스트입니다.

하이라이트 그룹을 변경하려면 nvim_set_hl()을 사용하여 직접 설정하세요.

비활성화

비활성화하려면 vim.g.minitest_disable(전역) 또는 vim.b.minitest_disable(버퍼용)을 true로 설정하세요. 다양한 시나리오와 커스터마이징 의도를 고려하여 모듈 기능 비활성화를 위한 정확한 규칙을 작성하는 것은 사용자의 몫으로 남겨둡니다. 일반적인 레시피는 mini.nvim-disabling-recipes를 참조하세요.

config

MiniTest.config

기본값

MiniTest.config = {
  -- 테스트 케이스 수집을 위한 옵션. `:h MiniTest.collect()` 참조.
  collect = {
    -- 'busted' 테스트 프레임워크의 함수를 일시적으로 에뮬레이션
    -- (`describe`, `it`, `before_each`, `after_each` 등)
    emulate_busted = true,

    -- 수집할 파일 경로 배열을 반환하는 함수.
    -- 기본값: 'tests' 디렉토리에서 'test_'로 시작하는 모든 Lua 파일.
    find_files = function()
      return vim.fn.globpath('tests', '**/test_*.lua', true, true)
    end,

    -- 테스트 케이스 실행 여부를 나타내는 서술어 함수
    filter_cases = function(case) return true end,
  },

  -- 테스트 케이스 실행을 위한 옵션. `:h MiniTest.execute()` 참조.
  execute = {
    -- 호출 가능한 필드 `start()`, `update()`, `finish()`를 가진 테이블
    reporter = nil,

    -- 첫 번째 에러 발생 시 실행을 중지할지 여부
    stop_on_error = false,
  },

  -- 프로젝트별 테스트 실행을 처리하는 스크립트 경로(현재 디렉토리 기준 상대 경로)
  script_path = 'scripts/minitest.lua',

  -- 에러가 아닌 피드백 표시를 비활성화할지 여부
  silent = false,
}

current

MiniTest.current

테스트 실행의 현재 상태에 대한 정보가 담긴 테이블

MiniTest.execute()의 결과를 검사하는 데 사용하세요. 매 호출 시작 시 초기화됩니다.

최소한 다음 키들이 지원됩니다:

  • <all_cases> - 현재 실행 중인 모든 케이스의 배열. 기본적으로 MiniTest.execute()의 입력값입니다.

  • <case> - 현재 실행 중인 테스트 케이스. MiniTest-test-case를 참조하세요. 실행 출력(커스텀 노트 추가 등)을 커스터마이징하는 데 사용하세요.

new_set()

MiniTest.new_set({opts}, {tbl})

테스트 세트 생성

테스트 세트는 두 가지 기본 데이터 구조 중 하나입니다. 이는 MiniTest-test-case를 통한 순차적 조직과 반대되는 계층적 테스트 조직을 정의하는 테이블입니다.

모든 요소는 다음 세 가지 카테고리 중 하나에 속합니다:

  • 호출 가능한 객체(함수 또는 __call 메타테이블 엔트리가 있는 테이블)는 테스트 동작을 정의하는 것으로 간주됩니다. 이는 “현재 인자”(중첩된 모든 parametrize 값의 결과, 후술함)와 함께 호출됩니다. 에러가 발생하면 테스트가 실패한 것입니다.

  • 테스트 세트(이 함수의 출력)는 중첩된 구조를 정의합니다. 수집 중 옵션(MiniTest.collect() 참조)은 이(부모) 테스트 세트의 옵션으로 확장됩니다.

  • 그 외의 요소는 헬퍼로 간주되며 테스트 구조에 직접 참여하지 않습니다.

세트 옵션을 통해 테스트 수집 및 실행을 커스터마이징할 수 있습니다 (opts 설명에 더 자세한 내용이 있습니다):

  • hooks - 테스트 실행의 미리 정의된 단계에서 인자 없이 호출될 요소가 있는 테이블입니다.

  • parametrize - 메인 테스트 동작이 호출될 다양한 인자를 정의하는 배열입니다. 사소하지 않은 매개변수화는 모든 요소(중첩된 것 포함)가 parametrize의 모든 요소에 대해 “복제”되어 처리되도록 합니다. 이를 통해 적은 노력으로 다양한 테스트 조합을 처리할 수 있습니다.

  • data - 케이스로 전달될 사용자 데이터가 담긴 테이블입니다. 주요 목적은 커스터마이징된 케이스 필터링에 사용되는 것입니다.

참고:

  • 요소를 추가하는 기본 방식은 T[name] = element 구문을 사용하는 것입니다. 이 방식을 사용하면 추가된 요소의 순서가 보존됩니다. 다른 방식은 순서를 보장하지 않습니다.

  • 제공된 옵션 opts는 메타테이블의 opts 필드(getmetatable(set).opts)에 저장됩니다.

매개변수

{opts} (table|nil) 허용되는 옵션:

  • <hooks> - 다음 필드를 가진 테이블:

    • <pre_once> - 필터링된 첫 번째 노드 전에 실행됩니다.

    • <pre_case> - 각 케이스(중첩된 케이스 포함) 전에 실행됩니다.

    • <post_case> - 각 케이스(중첩된 케이스 포함) 후에 실행됩니다.

    • <post_once> - 필터링된 마지막 노드 후에 실행됩니다.

  • <parametrize> - 각 요소 자체가 호출 가능한 필드의 “현재 매개변수”에 추가될 매개변수 배열인 배열입니다. 참고: {}는 “매개변수화 결과 케이스 0개”와 동일하므로 평범한 {}를 사용하지 마세요. 이 세트에서는 어떤 케이스도 수집되지 않습니다. 매개변수 없이 테스트 동작을 호출하는 것은 {{}}를 사용하거나 parametrize 옵션을 아예 제공하지 않는 것과 동일합니다.

  • <data> - 케이스로 전달될 사용자 데이터입니다. 더 세밀한 필터링에 사용될 수 있습니다.

  • <n_retry> - 성공할 때까지 각 케이스를 재시도할 횟수입니다. 기본값: 1.

{tbl} (table|nil) 초기 테스트 항목(중첩 가능). 순서에 대한 보장 없이 실행됩니다.

반환

(table) 단일 테스트 세트.

사용법

-- 기본값 사용
T = MiniTest.new_set()
T['works'] = function() MiniTest.expect.equality(1, 1) end

-- 커스텀 옵션 사용. 이는 실제 두 개의 케이스로 결과가 나옵니다: 첫 번째는
-- 통과하고, 두 번째는 두 번의 시도 후 실패합니다.
T['nested'] = MiniTest.new_set({
  hooks = { pre_case = function() _G.x = 1 end },
  parametrize = { { 1 }, { 2 } },
  n_retry = 2,
})

T['nested']['works'] = function(x) MiniTest.expect.equality(_G.x, x) end

테스트 케이스

테스트 케이스

테스트 세트를 통한 계층적 조직(참조 MiniTest.new_set())과 반대되는 순차적 테스트 조직의 항목입니다. 테스트 실행의 모든 필요한 정보를 나타내기 위해 MiniTest.collect()를 통한 테스트 수집 결과로 생성됩니다.

테스트 케이스 실행은 다음 규칙을 따릅니다:

  • 다음 순서로 함수를 호출합니다:

    • hooks.pre의 모든 요소를 첫 번째부터 마지막까지 인자 없이 호출합니다.

    • args에서 언팩된 인자와 함께 test 필드를 호출합니다. 실행이 실패하면, 첫 번째 성공할 때까지(성공한다면) 최대 n_retry 번 재시도합니다 (pre_case 및 post_case에서 오는 훅과 함께).

    • hooks.post의 모든 요소를 첫 번째부터 마지막까지 인자 없이 호출합니다.

  • 모든 호출에서의 에러는 exec.fails에 추가됩니다. 즉, 어떤 훅에서의 에러도 테스트 실패로 이어집니다.

  • 상태(exec.state)는 매 호출 전과 마지막 호출 후에 변경됩니다.

클래스

{Test-case}

필드

{args} (table) test 호출 시 사용될 인자 배열입니다.

{data} (table) 사용자 데이터: 중첩된 테스트 세트의 opts.data의 모든 필드입니다.

{desc} (table) 설명: 중첩된 테스트 세트의 필드 배열입니다.

{exec} (table|nil) 테스트 케이스 실행에 대한 정보입니다. nil 값은 이 특정 케이스가 아직 실행되지 않았음을 의미합니다. 다음 필드를 가집니다:

  • <fails> - 실패 정보가 담긴 문자열 배열입니다.

  • <notes> - 실패하지 않은 정보가 담긴 문자열 배열입니다.

  • <state> - 테스트 실행 상태입니다. 다음 중 하나입니다:

    • ‘Executing <실행 중인 항목 이름>’ (실행 중).

    • ‘Pass’ (실패 없음, 노트 없음).

    • ‘Pass with notes’ (실패 없음, 일부 노트 있음).

    • ‘Fail’ (일부 실패, 노트 없음).

    • ‘Fail with notes’ (일부 실패, 일부 노트 있음).

{hooks} (table) 테스트 케이스의 일부로 실행될 훅입니다. 다음 필드를 가집니다:

  • <pre> 및 <post> - test가 실행될 때마다 전후에 연속적으로 실행될 함수 배열입니다.

  • <pre_source> 및 <post_source> - <pre> 및 <post> 배열의 해당 요소의 소스가 담긴 문자열 배열입니다. 소스는 "once" (pre_once 및 post_once 훅용) 와 "case" (pre_case 및 post_case 훅용) 중 하나입니다.

{test} (function|table) 테스트 동작을 나타내는 메인 호출 가능 객체입니다.

collect()

MiniTest.collect({opts})

테스트 케이스 수집

수집 프로세스 개요:

  • opts.emulate_busted가 true이면, 특별한 전역 함수를 일시적으로 만듭니다 (수집이 끝나면 제거됨). 이들은 테스트 파일 내부에서 테스트 케이스의 계층 구조를 생성하는 데 사용될 수 있습니다.

  • opts.find_files의 배열 출력에서 각 파일을 소싱합니다. 이는 테스트 세트(MiniTest.new_set() 참조)를 출력하거나, (“busted” 스타일이 사용되는 경우) nil을 출력해야 합니다 (테스트 세트는 암시적으로 생성됨).

  • 모든 테스트 세트를 파일 경로와 동일한 필드를 가진 단일 세트로 결합합니다.

  • 계층적 테스트 구성에서 순차적 구성으로 변환합니다: 단일 테스트 세트에서 테스트 케이스(MiniTest-test-case 참조) 배열로 변환합니다. 변환은 “모든 테이블 요소에 대해: 모든 parametrize 요소에 대해: …” 형식으로 수행됩니다. 세부 사항:

    • 요소가 호출 가능한 객체이면, 이를 메인 test 동작으로 하여 테스트 케이스를 구성합니다. 설명(Description)은 현재 테스트 세트 테이블에 있는 요소의 키와 함께 추가됩니다. 훅, 인자 및 데이터는 “현재 중첩된” 것들로부터 가져옵니다. 케이스를 출력 배열에 추가합니다.

    • 요소가 테스트 세트이면, 유사한 재귀적 방식으로 처리합니다. “현재 중첩된” 정보가 확장됩니다:

      • args는 parametrize의 “현재 요소”로 확장됩니다.

      • desc는 요소 키와 함께 추가됩니다.

      • hooks는 적절한 위치에 추가됩니다. *_case 훅은 부모 테스트 세트의 훅보다 모든 자식 케이스에 더 가깝게 삽입됩니다: pre_case는 끝에, post_case는 시작에 삽입됩니다.

      • data는 vim.tbl_deep_extend()를 통해 확장됩니다.

    • 그 외의 다른 요소는 처리되지 않습니다.

  • opts.filter_cases로 배열을 필터링합니다. 입력 케이스에는 모든 훅이 포함되어 있지 않으며, *_once 훅은 필터링 후에 추가됩니다.

  • 적절한 케이스에 *_once 훅을 추가합니다.

매개변수

{opts} (table|nil) 케이스 수집을 제어하는 옵션입니다. 가능한 필드:

  • <emulate_busted> - ‘lunarmodules/busted’ 인터페이스를 에뮬레이션할지 여부입니다. 이 전역 함수들을 에뮬레이션합니다: describe, it, setup, teardown,

    before_each, after_each. pending() 대신 MiniTest.skip()을 사용하고,

    finally 대신 MiniTest.finally()를 사용하세요.

  • <find_files> - 인자 없이 호출될 때 파일 경로 배열을 반환하는 함수입니다. 각 파일은 단일 테스트 세트 또는 nil을 반환하는 Lua 파일이어야 합니다.

  • <filter_cases> - 단일 테스트 케이스(MiniTest-test-case 참조)와 함께 호출될 때 이 케이스를 필터링해야 하면 false, 그렇지 않으면 true를 반환하는 함수입니다.

테스트 케이스 배열 실행

실행 프로세스 개요:

  • cases 입력으로 MiniTest.current의 all_cases를 초기화합니다.

  • reporter.start(cases)를 호출합니다 (존재하는 경우).

  • 각 케이스를 자연스러운 배열 순서(정수 키와 정렬됨)로 실행합니다. MiniTest.current.case를 현재 실행 중인 케이스로 설정합니다. 자세한 테스트 케이스 실행은 MiniTest-test-case에 설명되어 있습니다. 상태 변경(케이스 재시도 시도 포함) 후에는 reporter.update(case_num)을 호출합니다 (존재하는 경우). 여기서 case_num은 현재 테스트 케이스의 정수 키입니다.

  • reporter.finish()를 호출합니다 (존재하는 경우).

참고:

  • 실행은 스케줄링을 통한 비동기 방식으로 수행됩니다. 이를 통해 실행 중에 의미 있는 진행 상황 보고를 할 수 있습니다.

  • 이 함수는 아무것도 반환하지 않습니다. 대신, 적절한 exec 필드로 cases를 즉석에서 업데이트합니다. 실행 결과를 보려면 MiniTest.current의 all_cases를 사용하세요.

{opts} (table|nil) 케이스 수집을 제어하는 옵션입니다. 가능한 필드:

  • <reporter> - 호출 가능한 필드 start, update, finish를 가질 수 있는 테이블입니다. 기본값: 대화형 사용 시 MiniTest.gen_reporter.buffer(), 헤드리스 사용 시 MiniTest.gen_reporter.stdout().

  • <stop_on_error> - 첫 번째 에러 발생 후 실행을 중지할지 여부입니다(MiniTest.stop() 참조). 기본값: false.

expect

MiniTest.expect

기대치 함수가 담긴 테이블

각 함수는 다음과 같이 동작합니다:

  • 기대치가 충족되면 조용히 true를 반환합니다.

  • 디버깅에 도움이 되는 정보와 함께 유익한 에러를 발생시킵니다. 더 많은 컨텍스트를 제공하기 위해 커스터마이징 가능한 실패 원인을 허용합니다.

사용법

local x = 1 + 1
MiniTest.expect.equality(x, 2) -- 통과
MiniTest.expect.equality(x, 1, { fail_reason = 'Not equal' }) -- 실패

expect.equality()

MiniTest.expect.equality({left}, {right}, {opts})

두 객체의 동등성 기대

동등성은 vim.deep_equal()을 통해 테스트됩니다. 또한 (차이점을 더 쉽게 찾을 수 있도록) 동등성에 대한 더 자세한 원인 계산을 시도합니다:

  • 타입이 다른 경우.

  • 문자열의 경우 길이가 다르거나 어떤 문자가 다른 경우.

  • 테이블의 경우 값이 다른 “키 브랜치(key branch)”를 실제 값과 함께 표시합니다. 단일 차이점만 표시되며, 더 많을 수 있습니다. 중첩되지 않은 테이블의 경우 키 브랜치는 그냥 키입니다. 차이점이 중첩된 테이블 내부에 있는 경우, 키 브랜치는 다른 값으로 가는 “중첩된 테이블을 통한 경로”를 보여줍니다. 예:

    local eq = MiniTest.expect.equality
eq({ 1, 2 }, { 1, 3 })         -- 키 브랜치는 `2`입니다.
eq({ 1, { 2 } }, { 1, 'c' })   -- 키 브랜치는 `2`입니다. ('c'는 테이블이 아님)
eq({ 1, { 2 } }, { 1, { 3 } }) -- 키 브랜치는 `2->1`입니다.

-- 키 브랜치는 `1->1->"a"` 또는 `1->1->"b"` 중 하나입니다.
eq({ { { a = 1 } } }, { { { b = 2 } } })

매개변수

gen_reporter.buffer()

MiniTest.gen_reporter.buffer({opts})

버퍼 리포터 생성

이는 대화형(헤드리스가 아님) 사용을 위한 기본 선택입니다. 전용 비터미널 버퍼가 있는 창을 열고 스로틀된 다시 그리기를 통해 업데이트합니다.

열린 버퍼에는 다음과 같은 유용한 Normal 모드 매핑이 있습니다:

  • <Esc> - 실행 중이면 테스트 실행을 중지합니다 (MiniTest.is_executing() 및 MiniTest.stop() 참조). 그렇지 않으면 창을 닫습니다.

  • q - 편의성 및 호환성을 위해 <Esc>와 동일합니다.

일반적인 아이디어:

  • 케이스 설명(desc 필드)의 첫 opts.group_depth 요소를 연결하여 케이스를 그룹화합니다. 기본값을 사용하면 수집된 파일별로 그룹화됩니다.

  • start()에서 얼마나 많은 실행이 예정되어 있는지 알 수 있도록 일부 통계를 보여줍니다.

  • update()에서 현재 그룹의 기호 개요와 현재 케이스의 상태를 보여줍니다. 각 기호는 하나의 케이스와 그 상태를 나타냅니다:

    • ? - 케이스 실행이 끝나지 않음.

    • o - 통과.

    • O - 노트와 함께 통과.

    • x - 실패.

    • X - 노트와 함께 실패.

  • finish()에서 케이스별로 정렬된 모든 실패와 노트를 보여줍니다.

매개변수

{opts} (table|nil) 옵션이 담긴 테이블입니다. 사용된 필드:

  • <group_depth> - 그룹화에 사용되는 케이스 설명의 첫 요소 개수(0일 수 있음)입니다. 값이 높을수록 출력의 입도가 높아집니다. 기본값: 1.

  • <throttle_delay> - 다시 그리기 사이의 최소 대기 시간(밀리초)입니다. 화면 깜빡임을 줄이지만 계산량은 줄이지 않습니다. 기본값: 10.

  • <window> - 열 창의 정의입니다. 다음 형태 중 하나를 취할 수 있습니다:

    • 호출 가능 객체. 출력이 대상 창 ID일 것으로 기대하고 호출됩니다 (출력이 nil이면 현재 창이 사용됨). 이를 사용하여 “일반” 창에서 엽니다 (function() vim.cmd('vsplit') end와 같이).

    • 테이블. nvim_open_win()의 config 인자로 사용됩니다. 기본값: 중앙에 위치한 플로팅 창을 위한 테이블입니다.

new_child_neovim()

MiniTest.new_child_neovim()

자식 Neovim 프로세스 생성

이는 ‘mini.test’ 방법론의 핵심 조각으로 설계된 객체를 생성합니다. RPC 메시지를 통해 상호작용하기 위한 편의성 헬퍼와 함께 별도의 (자식) Neovim 프로세스(헤드리스지만 완전히 기능함)를 시작/중지/재시작할 수 있습니다.

자세한 내용은 MiniTest-child-neovim을 참조하세요.

반환

(MiniTest.child) MiniTest-child-neovim 객체입니다.

사용법

-- 초기화
local child = MiniTest.new_child_neovim()
child.start()

-- API 함수 사용
child.api.nvim_buf_set_lines(0, 0, -1, true, { 'Line inside child Neovim' })

-- Lua 코드, Vim스크립트 명령어 등 실행
child.lua('_G.n = 0')
child.cmd('au CursorMoved * lua _G.n = _G.n + 1')
child.type_keys('l')
print(child.lua_get('_G.n')) -- 1이어야 함

-- 다른 `vim.xxx` Lua 래퍼 사용 (자식 프로세스 내부에서 실행됨)
vim.b.aaa = 'current process'
child.b.aaa = 'child process'
print(child.lua_get('vim.b.aaa')) -- 'child process'여야 함

-- 프로세스가 더 이상 필요하지 않으면 항상 중지
child.stop()

자식 neovim

자식 클래스

어떤 테스트 동작에서도 신선한 프로세스를 사용할 수 있게 함으로써 신뢰할 수 있고 재현 가능한 테스트를 작성하기 위한 훌륭한 도구 세트를 제공합니다. 상호작용은 RPC 프로토콜을 통해 이루어집니다.

매우 유연하지만, 현재 몇 가지 제한 사항이 있습니다:

  • 자식의 입력과 출력 모두에 함수나 사용자 데이터(userdata)를 사용하는 것을 허용하지 않습니다. 일반적인 해결책은 계산을 현재 Neovim 프로세스에서 자식 프로세스로 옮기는 것입니다. 이를 위해 child.lua()와 child.lua_get()을 사용하세요.

  • 테스트를 작성할 때 “중단(hanging)” 프로세스로 끝나는 경우가 흔합니다: 출력 없이 실행이 멈춥니다. 대부분의 경우 Neovim 프로세스가 “차단(blocked)”되었기 때문입니다. 즉, 사용자 입력을 기다리고 있으며 다른 호출(예: child.api.nvim_exec_lua())에서 반환되지 않습니다. 일반적인 원인은 활성화된 hit-enter-prompt (프롬프트 높이를 더 큰 값으로 늘리세요) 또는 Operator-pending 모드 (종료하세요) 입니다. 이러한 경험을 완화하기 위해 대부분의 헬퍼는 즉각적인 실행이 중단 상태로 이어질 경우 에러를 발생시킵니다. 또한 중단 상태인 경우 child.api 대신 child.api_notify를 시도해 보세요.

참고:

  • 중요한 필드 유형은 “리디렉션 테이블”입니다. 이는 해당 vim.* 테이블에 대한 편의성 래퍼 역할을 합니다. 값을 반환하거나 설정하는 데 모두 사용될 수 있습니다. 예:

    • child.api.nvim_buf_line_count(0)는 자식 프로세스 내부에서 vim.api.nvim_buf_line_count(0)를 실행하고 그 출력을 현재 프로세스로 반환합니다.

    • child.bo.filetype = 'lua'는 자식 프로세스 내부에서 vim.bo.filetype = 'lua'를 실행합니다. 이들은 여전히 위에서 나열한 것과 동일한 제한 사항을 가지고 있으므로 완벽하지 않습니다. 의심스러운 경우에는 child.lua()를 사용하세요.

  • 거의 모든 메서드는 vim.rpcrequest()를 사용합니다 (즉, 호출이 완료될 때까지 기다린 다음 값을 반환합니다). vim.rpcnotify()를 사용하려면 *_notify 변형을 확인하세요.

  • 모든 필드와 메서드는 :가 아니라 .으로 호출해야 합니다.

자식 neovim start()

child.start({args}, {opts})

자식 프로세스를 시작하고 연결합니다. 자식이 이미 실행 중이면 작동하지 않습니다.

매개변수

{args} (table) 실행 파일을 위한 인자 배열입니다. 다음 기본 인자들이 앞에 추가됩니다 (startup-options 참조):

{ '--clean', '-n', '--listen', <some address>,
  '--headless', '--cmd', 'set lines=24 columns=80' }

{opts} (table|nil) 옵션:

  • <nvim_executable> - Neovim 실행 파일 이름입니다. 기본값: v:progpath.

  • <connection_timeout> - 이 밀리초가 지나면 연결 시도를 중단합니다. 기본값: 5000.

사용법

child = MiniTest.new_child_neovim()

-- 기본 clean Neovim 인스턴스 시작
child.start()

-- 커스텀 'init.lua' 파일과 함께 시작
child.start({ '-u', 'scripts/minimal_init.lua' })

자식 neovim type_keys()

child.type_keys({wait}, {…})

기본적으로 자식 프로세스 내부에서 적용되는 nvim_input()용 래퍼입니다. 차이점:

  • 각 문자 그룹 후에 대기할 수 있습니다.

  • 키 입력 결과 자식 프로세스에서 에러가 발생한 경우 (v:errmsg가 업데이트된 경우) 에러를 발생시킵니다.

  • 별도 엔트리로서의 키 ‘<’는’<LT>’로 이스케이프할 필요가 없을 수도 있습니다.

매개변수

{wait} (number|nil) 각 엔트리 후 대기할 시간(밀리초)입니다. 생략될 수 있으며, 이 경우 대기하지 않습니다.

{…} (string|table<number,string>) nvim_input()을 위한 별도 엔트리들이며, 이후 wait가 적용됩니다. 문자열이나 문자열 배열일 수 있습니다.

사용법

-- 이 모든 것들은 'c', 'a', 'w' 키를 입력합니다.
child.type_keys('caw')
child.type_keys('c', 'a', 'w')
child.type_keys('c', { 'a', 'w' })

-- `c` 이후와 'w' 이후에 5ms 대기합니다.
child.type_keys(5, 'c', { 'a', 'w' })

-- 특수 키도 사용될 수 있습니다.
child.type_keys('i', 'Hello world', '<Esc>')

자식 neovim get_screenshot()

child.get_screenshot({opts})

(기본 TUI) 화면에 표시되는 내용과 표시되는 방식을 계산합니다. 이는 기본적으로 모든 보이는 셀(1부터 ’lines’까지의 행, 1부터 ’columns’까지의 열)에 대해 screenstring() 및 screenattr()을 호출합니다.

참고:

  • 출력을 더 이식성 있고 시각적으로 유용하게 만들기 위해, screenattr()의 출력은 단일 문자 기호로 코딩됩니다. 이들은 94개 문자(33에서 126 사이의 ASCII 코드)에서 가져오므로, 텍스트가 표시되는 방식이 94가지보다 많으면 중복이 발생할 수 있습니다.

매개변수

{opts} (table|nil) 옵션. 가능한 필드:

  • <redraw> (boolean) - 스크린샷을 계산하기 전에 :redraw를 호출할지 여부입니다. 기본값: true.

반환

(table|nil) 다음 필드를 가진 스크린샷 테이블입니다:

  • <text> - 특정 셀에 표시되는 단일 문자의 “2D 배열”(행-열)입니다.

  • <attr> - 텍스트가 표시되는 방식(기본적으로 “코딩된” 외관/하이라이팅)을 나타내는 기호의 “2D 배열”(행-열)입니다. 이들은 서로 간의 관계에서만 사용되어야 합니다: 두 셀에 대해 동일한/다른 기호는 동일한/다른 시각적 외관을 의미합니다. 참고: 속성 값이 94개보다 많으면 위양성(false positive)이 발생할 수 있습니다. 또한 단일 문자열로 변환하기 위해 tostring()과 함께 사용될 수 있습니다 (레퍼런스 파일 작성에 사용됨). 이는 text와 attr에 대해 (빈 라인으로 구분된) 두 개의 시각적 부분으로 결과가 나옵니다. 각 부분은 내용 위에 “룰러(ruler)”가 있고 각 라인에 라인 번호가 있습니다. 적절한 스크린샷을 가져올 수 없으면 nil을 반환합니다.

사용법

local screenshot = child.get_screenshot()

-- row=3, column=4에 표시된 문자 표시
print(screenshot.text[3][4])

-- 문자열로 변환
tostring(screenshot)
