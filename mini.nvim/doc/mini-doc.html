mini.doc Neovim 도움말 파일 생성

MIT License Copyright (c) 2022 Evgeni Chasnovski

모듈

주요 설계 아이디어:

  • EmmyLua 스타일의 어노테이션 주석을 작성하여 코드 옆에 문서를 유지합니다. 주석은 있는 그대로 파싱되므로, 형식은 help-writing의 내장 가이드를 따라야 합니다. 하지만 더 세밀한 출력 도움말 파일 관리를 위해 많은 생성 단계에서 사용자 정의 훅이 허용됩니다.

  • 생성은 정해진 순서의 파일 세트를 한 줄씩 처리하여 수행됩니다. 각 줄은 (특정 설정 가능한 패턴과 일치하는 경우) 문서화 블록의 일부로 간주되거나, 그렇지 않은 경우 문서화 블록의 “애프터라인(afterline)”으로 간주될 수 있습니다. 자세한 내용은 MiniDoc.generate()를 참조하세요.

  • 도움말 파일의 특정 부분을 설명하는 중첩된 데이터 구조(섹션, 블록, 파일, 문서)를 사용하여 처리가 수행됩니다. 자세한 내용은 MiniDoc-data-structures를 참조하세요.

  • 프로젝트별 스크립트는 설정 가능한 경로를 가진 일반 Lua 파일로 작성할 수 있습니다. 자세한 내용은 MiniDoc.generate()를 참조하세요.

하지 않는 작업:

  • 어노테이션 내부에서 마크다운이나 다른 마크업 언어를 지원하지 않습니다.

  • 기본적인 작업(어노테이션 파싱, 포맷팅, 태그 자동 생성 등)을 위해 트리시터(treesitter) 대신 Lua 문자열 조작을 사용합니다. 이는 복잡성을 관리하고 의존성을 없애기 위함입니다.

설정

이 모듈은 require('mini.doc').setup({})을 통한 설정이 필요합니다 ({}를 사용자 config 테이블로 대체). 그러면 스크립팅이나 수동으로 사용할 수 있는 전역 Lua 테이블 MiniDoc이 생성됩니다 (예: :lua MiniDoc.*).

사용 가능한 설정 옵션은 MiniDoc.config를 참조하세요.

MiniDoc.config와 동일한 구조를 가진 vim.b.minidoc_config를 사용하여 버퍼별로 런타임 설정을 재정의할 수 있습니다. 자세한 내용은 mini.nvim-buffer-local-config를 참조하세요.

모듈이 에러가 아닌 피드백을 표시하지 않게 하려면 config.silent = true로 설정하세요.

팁

  • 어노테이션 주석 작성을 더 쉽게 만들어 줄 수 있는 몇 가지 설정 팁:

    • EmmyLua 스타일의 --- 주석 리더를 존중하도록 lua 파일 타입에 적절한 ’comments’를 설정하세요. :---,:-- 값이 잘 작동하는 것 같습니다.

    • 적절한 ’formatoptions’를 설정하세요 (fo-table 참조). j, n, q, r 플래그 추가를 고려해 보세요.

    • 목록 자동 포맷팅을 돕기 위해 적절한 ’formatlistpat’을 설정하세요 (’formatoptions’에 n 플래그가 추가된 경우). 한 가지 제안(완벽하지는 않음)은 ^\s*[0-9\-\+\*]\+[\.\)]*\s\+ 값입니다. 이는 ’적어도 하나의 특수 문자(숫자, -, +, *) 뒤에 문장 부호(. 또는 ))가 올 수도 있고, 그 뒤에 적어도 하나의 공백이 오면 목록 항목의 시작’으로 읽힙니다.

  • 아마도 이 모듈을 사용할 때 가장 권장되는 관행에 대한 신뢰할 수 있는 리소스 중 하나는 이 플러그인 전체일 것입니다. 참고를 위해 소스 코드를 살펴보세요.

비교

  • tjdevries/tree-sitter-lua:

    • 주요 설계는 Lua 코드와 어노테이션 주석을 모두 파싱하기 위해 트리시터 문법을 사용하는 것입니다. 이로 인해 설치, 사용자 정의 및 지원이 쉽지 않습니다.

    • 출력 포맷팅 자동화(자동 들여쓰기 및 줄 너비 맞춤 등)에 더 많은 신경을 씁니다. 이 플러그인은 사용자 정의 후처리 훅을 제공하는 옵션과 함께 수동 포맷팅에 더 치중합니다.

데이터 구조

데이터 구조

데이터 구조는 기본적으로 일부 필드(데이터 값을 가진 키)와 메서드(함수 값을 가진 키)가 동반된 다른 구조들의 배열입니다:

  • 섹션 구조 (Section structure)는 어노테이션 주제의 한 측면(‘@param’, ‘@return’, ’@text’와 같은 섹션 ID로 결정됨)을 설명하는 문자열 줄들의 배열입니다. 모든 줄은 도움말 파일에서 직접 사용됩니다.

  • 블록 구조 (Block structure)는 함수, 테이블, 개념과 같은 하나의 어노테이션 주제를 설명하는 섹션들의 배열입니다.

  • 파일 구조 (File structure)는 디스크의 특정 파일을 설명하는 블록들의 배열입니다. 기본적으로 파일은 연속된 블록으로 나뉩니다: 어노테이션 줄은 블록 내부로 들어가고, 비-어노테이션 줄은 정보의 block_afterlines 요소 내부로 들어갑니다.

  • 문서 구조 (Doc structure)는 최종 도움말 파일을 설명하는 파일들의 배열입니다. 섹션의 각 문자열 줄은 (깊이 우선 방식으로 탐색될 때) 출력 파일로 직접 들어갑니다.

모든 구조는 다음 키들을 가집니다:

  • 필드:

    • info - 현재 구조에 대한 추가 정보를 포함합니다. 자세한 내용은 다음 섹션을 참조하세요.

    • parent - 부모 구조의 테이블입니다 (존재하는 경우).

    • parent_index - 부모 배열에서 이 구조의 인덱스입니다. 부모의 현재 구조 근처에 다른 구조를 추가할 때 유용합니다.

    • type - 구조 타입(section, block, file, doc)을 나타내는 문자열입니다.

  • 메서드 (x:method(args)와 같이 사용):

    • insert(self, [index,] child) - self의 index 위치에 child를 삽입합니다 (선택 사항; 제공되지 않으면 자식은 끝에 추가됨). 기본적으로 table.insert()와 같지만, self를 적절히 업데이트하면서 child에 parent 및 parent_index 필드를 추가합니다.

    • remove(self [,index]) - self의 index 위치에서 요소를 제거합니다. 기본적으로 table.remove()와 같지만, self를 적절히 업데이트합니다.

    • has_descendant(self, predicate) - predicate가 true를 반환하는 자손(구조 또는 문자열)이 있는지 여부입니다. 성공할 경우 첫 번째 자손을 두 번째 값으로 반환합니다.

    • has_lines(self) - 구조에 출력 파일에 넣을 줄(빈 줄 포함)이 있는지 여부입니다. 섹션 구조의 경우 #self와 동일하지만, 더 높은 순서의 구조에 더 유용합니다.

    • clear_lines(self) - 구조에서 모든 줄을 제거합니다. 결과적으로 이 구조는 출력 도움말 파일에 기여하지 않게 됩니다.

구조 타입별 info 필드 설명:

  • 섹션 (Section):

    • id - 캡처된 섹션 식별자입니다. 식별자가 캡처되지 않았음을 의미하는 빈 문자열일 수 있습니다.

    • line_begin - 섹션이 시작되는 파일 내부의 줄 번호입니다 (파일에서 생성되지 않은 경우 -1).

    • line_end - 섹션이 끝나는 파일 내부의 줄 번호입니다 (파일에서 생성되지 않은 경우 -1).

  • 블록 (Block):

    • afterlines - 이 어노테이션 블록 이후(다음 블록 또는 파일 끝까지) 파일에서 파싱된 문자열 배열입니다. 문서화되는 대상에 대해 자동화된 결정을 내리는 데 유용합니다.

    • line_begin - 블록이 시작되는 파일 내부의 줄 번호입니다 (-1 if not generated from file).

    • line_end - 블록이 끝나는 파일 내부의 줄 번호입니다 (-1 if not generated from file).

  • 파일 (File):

    • path - 파일의 절대 경로입니다 (파일에서 생성되지 않은 경우 '').

  • 문서 (Doc):

    • input - 입력 파일 경로들의 배열입니다 (MiniDoc.generate()에서와 동일).

    • output - 출력 경로입니다 (MiniDoc.generate()에서와 동일).

    • config - 사용된 설정입니다 (MiniDoc.generate()에서와 동일).

기본값

MiniDoc.config = {
  -- 어노테이션을 나타내는 데 사용되는 줄의 일부를 추출하는 함수.
  -- 자세한 정보는 |MiniDoc.config|의 '참고'를 참조하세요.
  annotation_extractor = function(l) return string.find(l, '^%-%-%-(%S*) ?') end,

  -- 첫 번째 캡처된 식별자 이전의 블록 어노테이션 줄의 식별자
  default_section_id = '@text',

  -- 문서 수명 주기의 특정 단계에서 적용될 훅. 입력을 제자리에서(in place)
  -- 수정해야 합니다 (새로운 것을 반환하지 않음).
  hooks = {
    -- 다른 어떤 것보다 먼저 블록에 적용됨
    block_pre = --<함수: 헤더 섹션(태그 및/또는 시그니처)을 유추함>,

    -- 다른 어떤 것보다 먼저 섹션에 적용됨
    section_pre = --<함수: 현재 별칭(aliases)을 대체함>,

    -- 섹션에 지정된 캡처된 ID가 있는 경우 적용됨
    sections = {
      ['@alias'] = --<함수: MiniDoc.current.aliases에 별칭을 등록함>,
      ['@class'] = --<함수>,
      ['@diagnostic'] = --<함수: 섹션 내용을 무시함>,
      -- 가장 일반적인 사용법은 |MiniDoc.afterlines_to_code|를 참조하세요
      ['@eval'] = --<함수: 줄을 평가하고 그 반환값으로 대체함>,
      ['@field'] = --<함수>,
      ['@overload'] = --<함수>,
      ['@param'] = --<함수>,
      ['@private'] = --<함수: 제거할 블록을 등록함>,
      ['@return'] = --<함수>,
      ['@seealso'] = --<함수>,
      ['@signature'] = --<함수: 문서화된 객체의 시그니처 형식을 맞춤>,
      ['@tag'] = --<함수: 해당 줄을 적절한 태그 줄로 바꿈>,
      ['@text'] = --<함수: 의도적으로 아무것도 하지 않음>,
      ['@toc'] = --<함수: 모든 섹션 줄을 비움>,
      ['@toc_entry'] = --<함수: 목차용 줄을 등록함>,
      ['@type'] = --<함수>,
      ['@usage'] = --<함수>,
    },

    -- 이전 모든 단계 이후에 섹션에 적용됨
    section_post = --<함수: 현재 아무것도 하지 않음>,

    -- 이전 모든 단계 이후에 블록에 적용됨
    block_post = --<함수: 많은 작업을 수행함>,

    -- 이전 모든 단계 이후에 파일에 적용됨
    file = --<함수: 구분 기호를 추가함>,

    -- 이전 모든 단계 이후에 문서에 적용됨
    doc = --<함수: 모델라인(modeline)을 추가함>,

    -- 출력 파일이 작성되기 전에 적용됨. 줄 배열을 인수로 받음.
    write_pre = --<함수: 상단의 구분 기호를 제거함>,

    -- 출력 도움말 파일이 작성된 후에 적용됨. 문서를 인수로 받음.
    write_post = --<함수: 다양한 편의 작업>,
  },

  -- 프로젝트별 도움말 파일 생성을 처리하는 스크립트의 경로
  -- (현재 디렉토리 기준). (사용자 정의 입력 파일, 훅 등)
  script_path = 'scripts/minidoc.lua',

  -- 에러가 아닌 피드백 표시를 비활성화할지 여부
  silent = false,
}

참고

  • annotation_extractor는 단일 문자열 줄을 입력으로 받습니다. 출력은 무엇이 입력을 어노테이션으로 만드는지(있다면) 설명합니다. 이는 하나의 캡처 그룹이 있는 string.find와 유사해야 합니다: 어노테이션 표시기의 시작과 끝(전체 부분이 도움말 줄에서 제거됨)이며, 세 번째 값은 섹션 ID 문자열입니다 (입력이 섹션의 첫 번째 줄을 설명하는 경우; 그렇지 않으면 nil 또는 빈 문자열). 줄이 어노테이션의 일부가 아닌 경우 출력은 nil이어야 합니다. 기본값은 어노테이션 줄이 다음과 같아야 함을 의미합니다:

    • 첫 번째 열에서 ---로 시작합니다.

    • --- 이후의 모든 공백이 아닌 문자는 새로운 섹션 ID로 취급됩니다.

    • 본문 텍스트 시작 부분의 단일 공백은 무시됩니다.

  • 훅은 함수여야 합니다. 기본값은 시간이 지남에 따라 변할 수 있는 많은 작업을 수행할 수 있으므로, 자세한 내용은 소스 코드를 살펴보세요. 더 많은 정보는 MiniDoc.default_hooks에서 찾을 수 있습니다.

current

MiniDoc.current

자동 생성의 현재 상태에 대한 정보가 담긴 테이블

MiniDoc.generate()의 시작과 끝에서 초기화됩니다.

적어도 다음 키들이 지원됩니다:

  • {aliases} - 키는 별칭 이름이고 값은 별칭 설명과 단일 문자열(줄 구분을 위해 \n 사용)인 테이블입니다.

  • {eval_section} - @eval 섹션 훅의 입력 섹션입니다. 현재 블록 등에 대한 정보로 사용될 수 있습니다.

  • {toc} - 목차 항목이 포함된 배열입니다. 각 항목은 전체 @toc_entry 섹션입니다.

default_hooks

MiniDoc.default_hooks

기본 훅

MiniDoc.config.hooks의 기본값입니다. 약간의 수정만 필요한 경우에 사용하세요.

동작에 대한 몇 가지 통찰:

  • 문서화된 객체 메타데이터(현재는 태그 및 객체 시그니처)의 기본 유추는 block_pre에서 수행됩니다. 유추는 문자열 패턴 매칭을 기반으로 하므로 잘못된 결과가 나올 수 있지만 대부분의 경우 잘 작동합니다. 의도적으로 블록 뒤의 첫 번째 줄에 들여쓰기가 없고 유추가 일어날지 결정하는 데 필요한 모든 정보가 포함된 경우에만 작동합니다.

  • “변수와 유사한” 객체(‘@class’, ‘@field’, ‘@param’)를 설명하는 섹션용 훅은 첫 번째 단어를 자동으로 ’{}’로 감쌉니다.

  • “타입과 유사한” 데이터(‘@field’, ‘@param’, ‘@return’, ‘@type’)를 가져야 하는 섹션용 훅은 가장 먼저 발견된 “타입과 유사한” 단어와 그 주변 문자를 자동으로 ’(<type>)’로 감쌉니다 (잘못된 결과가 나올 수 있음). 알고리즘이 100% 정확하지는 않지만 현재 허용된 타입 어노테이션에서는 잘 작동하는 것 같습니다. 허용된 타입에 대해서는 https://github.com/sumneko/lua-language-server/wiki/EmmyLua-Annotations#types-and-type 을 참조하거나 소스 코드를 확인하세요.

  • 목차(TOC)의 자동 생성은 다음과 같은 방식으로 수행됩니다:

    • 어노테이션 블록에 @toc_entry ID가 있는 섹션을 넣습니다. 섹션의 줄들이 목차 항목으로 등록됩니다.

    • 렌더링된 목차를 삽입하고 싶은 곳에 @toc 섹션을 넣습니다. 목차 항목은 왼쪽에 삽입되고, 각각의 태그 섹션(있는 경우 첫 번째만)에 대한 참조는 오른쪽에 삽입됩니다. 렌더링은 기본 doc 훅에서 수행됩니다 (모든 파일 처리가 끝난 후에 수행되어야 하기 때문입니다).

  • write_post 훅은 반복적인 어노테이션 작성을 위해 편리한 몇 가지 작업을 실행합니다:

    • 출력 파일을 포함하는 디렉토리에 대해 :helptags를 생성합니다.

    • 출력 파일을 포함하는 버퍼를 자동으로 다시 로드합니다 (존재하는 경우).

    • 결과에 대한 알림 메시지를 표시합니다.

generate()

MiniDoc.generate({input}, {output}, {config})

도움말 파일 생성

알고리즘

  • 도움말 생성을 위한 주요 매개변수는 입력 파일 경로들의 배열과 출력 도움말 파일 경로입니다.

  • 모든 입력을 파싱합니다:

    • 각 파일에 대해, 문서화 블록 배열을 생성하기 위해 줄들이 위에서 아래로 처리됩니다. 각 줄은 MiniDoc.config.annotation_extractor를 적용하여 어노테이션인지 테스트됩니다: 무언가 추출되면 어노테이션으로 간주됩니다. 어노테이션 줄은 추출된 어노테이션 표시기를 제거한 후 “현재 블록”으로 들어가고, 그렇지 않으면 “현재 블록”의 애프터라인(afterlines)으로 들어갑니다.

    • 각 블록의 어노테이션 줄은 위에서 아래로 처리됩니다. 줄에 캡처된 섹션 ID가 있으면 “현재 섹션”의 첫 번째 줄입니다 (첫 번째 블록 줄은 섹션 ID를 지정하지 않을 수 있으며, 기본값은 @text입니다). 캡처된 섹션 ID가 없는 모든 후속 줄은 “현재 섹션”으로 들어갑니다.

  • 구조 훅을 적용합니다 (모든 입력의 ‘테이블 특성’ 덕분에 입력을 제자리에서 수정해야 함):

    • 각 블록은 MiniDoc.config.hooks.block_pre에 의해 처리됩니다. 이는 설명된 어노테이션 주제(ID가 @tag, @type인 섹션 등)로부터 섹션을 자동 생성하기 위한 지정된 단계입니다.

    • 각 섹션은 MiniDoc.config.hooks.section_pre에 의해 처리됩니다.

    • 각 섹션은 해당되는 MiniDoc.config.hooks.sections 함수에 의해 처리됩니다 (테이블 키는 섹션 ID와 같음). 이는 대부분의 포맷팅이 일어나야 하는 단계입니다 (@param 섹션의 첫 번째 단어를 {와 }로 감싸기, 섹션에 빈 줄 추가 등).

    • 각 섹션은 MiniDoc.config.hooks.section_post에 의해 처리됩니다.

    • 각 블록은 MiniDoc.config.hooks.block_post에 의해 처리됩니다. 이는 포맷팅이 완료된 후 블록을 처리하기 위한 단계입니다 (구분 기호 ----가 있는 첫 번째 줄 추가 등).

    • 각 파일은 MiniDoc.config.hooks.file에 의해 처리됩니다. 이는 파일 관련 데이터(구분 기호 ====가 있는 첫 번째 줄 추가 등)를 추가하기 위한 단계입니다.

    • 문서는 MiniDoc.config.hooks.doc에 의해 처리됩니다. 이는 도움말 파일 관련 데이터(목차 등)를 추가하기 위한 단계입니다.

  • 깊이 우선 방식으로 섹션의 모든 문자열을 수집합니다 (중첩된 “모든 파일 -> 모든 블록 -> 모든 섹션 -> 모든 문자열 -> 출력에 문자열 추가”와 동일). 문자열은 새로운 줄의 시작을 나타내는 \n 문자를 가질 수 있습니다.

  • 수집된 문자열을 MiniDoc.config.write_pre로 수정합니다. 이전 단계의 문자열을 입력으로 받고 문자열 배열을 반환해야 합니다.

  • 수정된 문자열을 출력 파일에 씁니다.

  • MiniDoc.config.write_post 훅을 실행합니다. 이는 피드백을 보여주거나 새로 업데이트된 도움말 파일과 관련된 작업(태그 생성 등)을 수행하는 데 유용합니다.

프로젝트별 스크립트

모든 인수가 기본 nil 값인 경우, 먼저 프로젝트별 스크립트를 소싱하려는 시도가 있습니다. 이는 기본적으로 현재 MiniDoc.config를 캐싱하고 복원하면서 현재 Lua 런타임으로 luafile <MiniDoc.config.script_path>를 수행하는 것입니다. 성공적으로 실행되면 더 이상의 생성 작업이 중단되며, 에러가 발생하면 스크립트가 발견되지 않은 것처럼 생성을 진행합니다.

전형적인 스크립트 내용에는 사용자 정의 훅 정의, 입력 및 출력 파일, 그리고 최종적인 require('mini.doc').generate() 호출(인수 포함 또는 미포함)이 포함될 수 있습니다.

매개변수

{input} (table|nil) 제공된 순서대로 처리될 파일 경로들의 배열입니다. 기본값: 현재 디렉토리의 모든 ‘.lua’ 파일과 ‘lua/’, ‘after/’, ‘colors/’ 서브디렉토리의 모든 해당 파일들입니다. 참고: 모든 ‘init.lua’ 파일은 동일한 디렉토리의 다른 파일보다 먼저 배치됩니다.

{output} (string|nil) 출력 도움말 파일의 경로입니다. 기본값: doc/<current_directory>.txt (플러그인용 도움말 파일 생성을 위해 설계됨).

{config} (table|nil) MiniDoc.config의 일부를 재정의하는 설정입니다.

반환값

(table) 생성되어 출력 도움말 파일에 사용된 문서 구조입니다. MiniDoc.config.script_path가 성공적으로 사용된 경우, 이 함수의 마지막 호출로부터의 반환값입니다.

afterlines_to_code()

MiniDoc.afterlines_to_code({struct})

애프터라인을 코드로 변환

이 함수는 특정 값(특히 테이블의 기본값)의 문서화를 자동화하기 위해 @eval 섹션과 함께 사용하도록 설계되었습니다. 특정 지시문에 따라 애프터라인(afterlines)을 처리하고 출력을 Lua 코드 블록처럼 보이게 만듭니다.

가장 일반적인 사용법은 어노테이션에 다음 섹션을 추가하는 것입니다:

---@eval return MiniDoc.afterlines_to_code(MiniDoc.current.eval_section)

지시문 (Directives)

지시문은 Lua 문자열 패턴 기능을 사용하여 처리되는 특수 주석입니다 (따라서 잘못된 결과에 주의하세요). 각 지시문은 별도의 줄에 놓여야 합니다. 지원되는 지시문:

  • --minidoc_afterlines_end는 애프터라인 끝 줄을 나타냅니다. 그 이전의 모든 줄만 애프터라인으로 간주됩니다. 사용해서는 안 되는 여분의 코드가 애프터라인에 있는 경우 유용합니다.

  • --minidoc_replace_start <replacement> 및 --minidoc_replace_end는 그 사이의 줄들이 <replacement>로 대체되어야 함을 나타냅니다. 함수 본문을 다른 것으로 교체하는 경우와 같이 출력에 배치될 내용을 수동으로 변경하는 데 유용합니다.

다음은 예시입니다. 다음과 같은 애프터라인이 있다고 가정해 보겠습니다:

--minidoc_replace_start {
M.config = {
  --minidoc_replace_end
  param_one = 1,
  --minidoc_replace_start param_fun = --<함수>
  param_fun = function(x)
    return x + 1
  end
  --minidoc_replace_end
}
--minidoc_afterlines_end

return M

@eval 섹션을 추가한 후에는 다음과 같이 형식이 지정됩니다:

{
  param_one = 1,
  param_fun = --<함수>
}

매개변수

{struct} (table) 애프터라인이 코드로 변환될 블록 또는 섹션 구조입니다.

반환값

(string|nil) 도움말 파일에서 애프터라인을 Lua 코드 블록으로 설명하는 단일 문자열(줄 구분을 위해 \n 사용)입니다. nil인 경우 입력이 유효하지 않습니다.
